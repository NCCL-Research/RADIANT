# RADIANT: comparative evaluation design draft

**Status:** Planning draft — not preregistered; no dataset or model evaluation has been run.  
**Scope:** Synthetic, researcher-authored mathematical reasoning cases only for the initial software study.

## 1. Research question

How reliably do eligible AI tutoring systems classify protocol-defined mathematical reasoning patterns from supplied intermediate work, and how sensitive are their diagnoses to controlled changes in that evidence?

The study must distinguish diagnosis correctness from explanation quality and feedback usefulness.

## 2. Scope boundary

The initial evaluation should be limited to the mathematical topics and task formats that can be specified and independently annotated. The current Noggimigo README documents three lessons: fractions_intro, algebra_intro, and patterns_sequences. Do not generalise results beyond the evaluated tasks, systems, prompts, and versions.

No real learner data, recruitment, or interaction is part of this initial synthetic benchmark. Any later study involving human participants, especially minors, requires the applicable ethics and fair rules to be checked before recruitment or data collection.

## 3. Stage 0 — system capability audit

The source-level Noggimigo review is recorded in [NOGGIMIGO_CAPABILITY_AUDIT.md](NOGGIMIGO_CAPABILITY_AUDIT.md); it is pinned to a specific Noggimigo commit and must be repeated if that implementation changes.

Before including a system in diagnostic-accuracy comparisons, document whether it can:

- receive the task prompt and intermediate work as separate inputs;
- return a diagnosis label in a documented, machine-readable format;
- abstain when evidence is insufficient;
- identify the exact evidence supporting its diagnosis;
- run under a frozen and reproducible version/configuration.

A system that only verifies final answers or generates tutoring language is not automatically a reasoning-diagnosis system. In particular, Noggimigo's deterministic answer-verification pathway and optional language-generation adapter must not be described as intermediate-work diagnosis unless an implemented, tested capability demonstrates that function.

Record unsupported capabilities as **not eligible for that analysis**, rather than treating missing output as an incorrect diagnosis or inventing a diagnosis interface.

## 4. Candidate system conditions

The following are candidate conditions, subject to Stage 0:

1. Noggimigo deterministic pathway.
2. Noggimigo with its optional local language-model adapter.
3. An ablation that removes the tutoring layer while retaining the same underlying model, if technically feasible and comparable.
4. An independent tutoring or language-model system with a documented version.

Do not compare systems as if they share the same capability when their input/output contracts differ. Freeze model identifiers, revision hashes where available, prompts, decoding parameters, software versions, and retry policy before evaluation.

## 5. Synthetic case construction

Create researcher-authored cases for the currently documented lesson areas. Each case should include:

- stable case and task identifiers;
- exact task wording;
- final answer;
- intermediate work;
- intended reference label, assigned independently of model outputs;
- evidence span(s) supporting the reference label;
- case provenance and authoring notes.

The taxonomy is not yet defined. Derive candidate categories from a documented review of the relevant mathematical concepts and common reasoning patterns, then write operational definitions and boundary examples. Include correct reasoning, distinguishable misconception patterns, mixed or ambiguous work, and insufficient evidence. Do not create labels that cannot be reliably distinguished from the supplied work.

Use a case-level split for development and held-out evaluation. Keep paraphrase and counterfactual variants of a source case in the same split to prevent leakage.

## 6. Paired robustness conditions

- **Paraphrase pairs:** preserve the mathematical reasoning and diagnostic evidence while changing surface wording. The expected diagnosis should remain unchanged.
- **Counterfactual pairs:** change one protocol-defined diagnostic cue while keeping irrelevant context as stable as possible. The expected diagnosis change (or non-change) must be specified before model evaluation.

Each pair needs an explicit construction rationale and an independent validity check. Do not assume a pair is valid merely because it was generated by a language model.

## 7. Outcomes

Report outcomes separately:

- diagnostic accuracy and macro-F1 on eligible labelled cases;
- per-class precision, recall, and confusion matrix;
- abstention rate and coverage;
- selective accuracy at stated coverage levels;
- paraphrase-pair invariance;
- counterfactual-pair response rate against the pre-specified expected change;
- evidence-span support, assessed with a separate rubric;
- explanation and feedback quality, assessed separately from label correctness.

Define the evidence-support rubric and annotation process before scoring. A fluent explanation is not proof of a correct diagnosis.

## 8. Annotation and quality control

Write an annotation manual before finalising the benchmark. Specify:

- operational label definitions and examples;
- evidence sufficiency rules;
- handling of mixed, ambiguous, and unclassifiable cases;
- independent annotation procedure;
- disagreement resolution and adjudication;
- agreement statistic and its limitations.

Reference labels must not be derived from model predictions. Preserve an audit trail for case revisions and exclusions.

## 9. Analysis and reporting

Specify the number of cases, class balance, paired-case counts, and uncertainty method before confirmatory evaluation. Account for dependence among variants derived from the same source case. Report denominators, per-class results, uncertainty, exclusions, and negative findings.

Do not rank systems using one aggregate score if their supported capabilities or evaluation coverage differ. Treat unsupported conditions and missing outputs according to a pre-defined policy.

## 10. Research integrity and next decisions

Before confirmatory evaluation, resolve:

1. Stage 0 capability audit and exact eligible systems.
2. Lesson/task scope and literature-grounded misconception taxonomy.
3. Case counts, class balance, and held-out split.
4. Annotation rubric, independent review, and adjudication.
5. Prompt/model/version freeze and run procedure.
6. Primary outcome, uncertainty method, and comparison strategy.
7. Whether the work remains a synthetic software benchmark or later seeks human-participant approval.

**Current status:** This document is a design draft only. No model has been evaluated, no diagnostic performance is claimed, and the synthetic benchmark has not yet been created.
